## Customising Spring Security

### 1. Require HTTPS requests

By default, Spring Security accepts both HTTP and HTTPS requests.
* To ensure that our application only accepts HTTPS, we configure our security filter chain with the **.requiresHttps()** method.
* This will redirect HTTP requests to HTTPS. We then specify within **.requestMatches()** which requests should be redirected to HTTPS.

### 2. Exception handling

There are two general exceptions that Spring Security handles: AuthenticationException (401) and AccessDeniedException (403). 
The ExceptionTranslationFilter handles these exception types by invoking one of the two interface implementations. 
We have to override the two interfaces (AuthenticationEntryPoint, AccessDeniedHandler) to implement our own logic and execute a custom response.

For 401 exceptions:
* We pass our custom AuthenticationEntryPoint implementation through the **httpBasicCustomizer** .authenticationEntryPoint method (for Http Basic authentication only).
* We can also perform configurations to the whole security filter chain by using the .exceptionHandling() method and passing it through the **exceptionHandlingConfig** .authenticationEntryPoint method.

For 403 exceptions:
* We pass our custom AccessDeniedHandler implementation through the **exceptionHandlingConfig** .accessDeniedHandler method. This is configured using the .exceptionHandling() method.

### 3. Session timeout and invalidating sessions

When we try to sign in, Spring Security creates a session cookie (JSESSIONID). The default timeout for this session cookie is 30 minutes of idle time.
* To customise the timeout, we can to specify the duration in our configuration file (application.yaml): server.servlet.session.timeout.
* To make it more user-friendly, we can redirect the user on timeout. We can configure the url via the .sessionManagement method and specifying the url in the **.invalidSessionUrl()** method.
* We can restrict the number of concurrent sessions the user can have by further using the **.maximumSessions()** method.

> **Session hijacking attacks** are where the attacker steals the session IDs for a web application by eavesdropping on communication between a user and an application or by gaining access to the user's computer or web browser data.
* This can be prevented by using HTTPS protocol for communication so session ID cannot be stolen, or limit the session ID to a short time.

> **Session fixation attacks** are where it is possible for an attacker to create a session by accessing a site, then persuading another user to log in with the same session. 
*  Spring Security protects against this automatically by creating a new session or otherwise changing the session ID when a user logs in (e.g. changeSessionId, newSession, migrateSession methods from sessionManagement in the filter chain).

### 4. Listening to authentication events

For each authentication that succeeds or fails, a AuthenticationSuccessEvent or AuthenticationFailureEvent are published by Spring Security framework.
The provided DefaultAuthenticationEventPublisher by Spring Security takes care of publishing these events to these listeners.
Based on our requirements, we can use @EventListener to listen to these events and execute our business logic.
